# Next steps to production

The repository already publishes an agent-agnostic REST boundary. It includes an OpenAPI 3.1 document at [`docs/schemas/openapi.json`](schemas/openapi.json), six JSON Schemas, and Pydantic contracts v0.2 in [`contracts/README.md`](../contracts/README.md). The contracts make money integer cents, keep unknown stock explicit, reject unknown fields, and expose decision reasons and optional confidence.

The remaining limits are explicit in code comments marked `ponytail`. Orders and audit use `data/orders.json` and `data/audit.jsonl`. Mandates use one in-code demo record. Auth uses shared environment keys. The quote cache and order lock are process-local. The audit reader scans the whole file. Catalogue matching is lexical. The Valio mock has price and availability endpoints, but no order endpoint.

Verified mock behavior is recorded in [`docs/valio-api-notes.md`](valio-api-notes.md), and technical choices are recorded in [`docs/DECISIONS.md`](DECISIONS.md).

Priorities below are the path from the demo boundary to a deployable service.

| Priority | Next step | Why | Rough work |
|---:|---|---|---|
| 1 | **Move state to Postgres, for example Aiven.** Replace `data/orders.json` and `data/audit.jsonl`. Add buyer and time indexes. Define retention and archival before pruning data. Keep audit rows append-only. Add a hash chain or signed checkpoints, a restricted write role, and a verification job. | Render disk is ephemeral. The current audit can grow without bound, and `audit_log()` rereads the whole file on every request. Judges and operators need an audit trail that survives redeploys and shows tampering. | Schema and migrations for orders, lines, mandates, and audit events; repository layer; retention job; chain/signature verification; migration and restore tests. Move the quote cache to shared storage or a shared cache when instances multiply. |
| 2 | **Replace shared keys with per-agent identity.** Use OAuth 2 client credentials or mTLS. Bind the identity to a buyer and scopes. Apply it to `POST /api/agent/run` as well as the order routes. Sign mandates and verify buyer, issuer, version, and expiry at the front door. | `auth.py` compares static `X-Agent-Key` and `X-Approver-Key` secrets from environment variables. The buyer must always come from the authenticated identity, never the body. A signed mandate makes the buyer's limits portable and verifiable. | Client or certificate registration, token/certificate validation, key rotation and revocation, mandate signature format and verification, error responses, and an updated OpenAPI security definition. |
| 3 | **Let buyers edit their own mandate.** Store versioned mandates instead of the seeded dict in `mandates.py`. Make the buyer identity come from the authenticated principal. Re-sign and audit every change. | The agent flow currently reads one server-side demo mandate, while `POST /api/orders` accepts a mandate in the request body after an identity check. Production needs one authoritative, buyer-controlled version. | Mandate API and UI, optimistic version checks, approval or re-authentication for changes, history, expiry handling, and tests for `this_order` versus `always` scope. |
| 4 | **Make order state safe across workers and instances.** Replace the in-process `asyncio.Lock` and in-memory store with database transactions. Lock the buyer's budget and pending order row when committing. Make approve, reject, and retries idempotent. | The service currently requires exactly one Uvicorn worker. A process-local lock cannot protect the weekly budget or an approval race across workers or instances. | Row locks or serializable transactions, unique idempotency keys, state-transition constraints, retry tests, and a final re-check after the Valio call and before commit. Keep slow Valio calls outside the transaction. |
| 5 | **Add signed quotes with expiry.** Extend the quote trust protocol with a provider signature, key id, canonical payload, requested date, fixed price, availability, `fetched_at`, and `valid_until`. The door verifies the signature and expiry before relying on a quote. | `Quote` already has freshness and expiry fields, but quotes are not signed. Today the door relies on its own live re-check and a process-local 60-second cache. A signed quote makes the fixed-price handoff auditable. | Agree the signature and key-discovery format with Valio, add verification and replay protection, expose failure reasons, and retain the signed payload in the audit. Keep live re-fetching until Valio supports the protocol. |
| 6 | **Integrate a real Valio order endpoint.** Keep the front-door decision and human approval step, then submit only a confirmed order. Support idempotency, acknowledgement, status, cancellation, and reconciliation. | The mock has no order endpoint. `/api/orders` currently records a local order after the gate; it does not place an order with Valio. | Confirm the Valio contract and sandbox, map the confirmed order to Valio fields, implement retries and status polling or callbacks, and test duplicate, rejected, and partial outcomes. |
| 7 | **Control Valio traffic.** Add a host-scoped rate limiter, bounded concurrency, backoff, and a circuit breaker. Retain static catalogue filtering, batching, and bounded caching. | Valio documents rate limits as undisclosed. The client has a 1,000-product batch limit and a 60-second in-process cache, but no outbound rate limiter. | Measure 429s and latency, set per-tenant budgets, handle `Retry-After`, share cache state across instances, and test bursts without scanning the catalogue. |
| 8 | **Add monitoring.** Expose more than the current liveness and configuration check. Measure Valio calls, cache age, quote expiry, decision outcomes, order transitions, approval lag, auth failures, and rate-limit responses. | The current health route is a liveness check. Production needs evidence when a quote is stale, an order is stuck, or Valio is failing. | Metrics, traces, structured redacted logs, dashboards, alerts, and a runbook. Do not log API keys, tokens, mandate signatures, or raw sensitive request text by default. |
| 9 | **Implement the Gemini Decisions API confidence path.** This is decided in [`docs/DECISIONS.md`](DECISIONS.md) as D3, but it is **not implemented yet**. The current Gemini calls use `generateContent` for parsing and catalogue ranking; `Decision.confidence` can remain null. Keep deterministic quantity, price, stock, and mandate checks authoritative. | Calibrated confidence can make the boundary between auto, human review, and decline visible. It must be measured, not treated as a raw model score. | Add the Decisions API integration, a labelled evaluation set, calibration and thresholds, fallback behavior, and audit fields for model, prompt, confidence, and rules version. Measure lexical menu-to-cart recall before adding embeddings. |
| 10 | **Add voice input.** D4 is decided, but the API currently accepts text only. The contracts allow `channel = voice`; there is no audio route or speech provider integration. | Voice is a planned input channel, not a current capability. The transcript and the buyer's confirmation must remain visible before an order is placed. | Add streamed or uploaded audio, speech-to-text, transcript review, `channel=voice`, language/error handling, and a confirmation step. Preserve the transcript in the audit with the same front-door rules. |
| 11 | **Export Peppol BIS Order / UBL.** Map a confirmed order, buyer, supplier, price, units, delivery date, and identifiers to the selected Peppol profile. Keep the internal contracts as the decision and audit model. | The current JSON contracts are open and documented, but they are not a trading-network order format. An export supports interoperability with procurement systems. | Define the mapping and missing master data, implement XML generation, validate against the selected BIS profile, and test round trips without changing the gate's net-cents semantics. |
| 12 | **Add an MCP server alongside REST.** Expose the same contract-backed search, quote, quantity, decision, and order tools. Keep REST and OpenAPI as the stable public boundary. | REST is implemented and documented. No MCP server exists in the repository. An adapter can serve agent-native clients without creating a second business-rule implementation. | Add an MCP adapter, tool schemas, per-tool auth and consent, pagination, timeouts, and tests that route every write through the same mandate, quote, gate, and audit path. |

The order is deliberate: durable state, identity, mandate authority, and concurrency come before external order submission. New channels and adapters should reuse the published contracts and the same front-door checks.
